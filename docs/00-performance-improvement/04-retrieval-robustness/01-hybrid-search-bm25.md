# Hybrid Search: BM25 보조 검색 도입 기록

- 작성일: 2026-08-06
- 상태: 구현 및 개발 데이터 비교 완료
- 비교 범위: 기존 24문항 중 검색 정답 조문이 있는 15문항의 법령 검색 결과. 최종 답변의 안전성 평가는 별도 과제

## 먼저 보는 결론

기존의 의미 검색(Dense Search)에 **단어·문자열이 실제로 겹치는지 보는 BM25**를
약하게 더했다. 두 결과를 같은 비중으로 섞으면 오히려 나빠졌고, BM25를 **보조 신호**로
낮은 비중만 주었을 때 개발 데이터의 Recall@5가 `0.711 → 0.744`로 늘었다.

다만 이것이 답변의 숫자까지 자동으로 맞게 만든 것은 아니다. 검색은 답변에 보여 줄
근거를 고르는 단계이고, 그 근거를 벗어나지 않고 답하는 일은 Agent 생성 단계에서
따로 검증해야 한다.

## 1. 관찰과 기준선

기존 법령 검색은 KURE-v1 임베딩으로 질문과 조문의 **의미가 가까운지**를 비교하는
Dense Search였다. 생활 표현을 이해하는 데는 좋지만, 법률명·조문 제목·금액처럼
정확한 단어가 중요한 질문에서 필요한 조문이 상위에 오지 않을 수 있었다.

예를 들어 `은행 파산 시 예금 보호 한도` 질문에서는 현행 기준인 `1억원`이 들어 있는
`예금자보호법 시행령 제18조`가 충분히 높게 나오지 않는 경우가 있었다. 로컬 XML도
확인한 결과, 해당 조문은 시행일 `2025-09-01` 기준 `1억원`으로 정상 보관되어 있었다.
즉 데이터가 오래된 문제가 아니라 **검색 결과를 고르는 문제**였다.

비교 전 Dense Search의 15개 검색 가능 개발 문항 평균은 다음과 같았다. 기존 24문항
전체 중 답변 경로·안내문을 확인하는 문항은 제외하고, 정답 조문이 지정된 문항만 검색
지표에 사용했다.

| 지표 | 의미 | Dense Search 기준선 |
| --- | --- | ---: |
| Precision@5 | 상위 5개 중 정답 조문 비율 | 0.280 |
| Recall@5 | 필요한 정답 조문을 상위 5개 안에서 찾은 비율 | 0.711 |

`@5`는 검색 결과를 5개까지 보여 주고 비교했다는 뜻이다. 이번 목적은 관련 조문을
더 놓치지 않는 것이므로 Recall도 함께 봤다.

## 2. 후보와 선택 근거

Hybrid Search는 서로 성격이 다른 두 검색을 함께 쓰는 방법이다.

```text
질문
 ├─ Dense Search: 질문과 조문의 뜻이 비슷한가?
 └─ BM25: 법률명·핵심 표현의 글자가 실제로 겹치는가?
                         ↓
             순위를 합쳐 상위 조문 선택
```

후보는 실제 같은 15개 개발 문항에서 하나씩 비교했다.

| 방법 | 결과와 판단 |
| --- | --- |
| 단어 단위 BM25를 Dense와 같은 비중으로 결합 | 미채택. 조사까지 붙은 단어를 그대로 비교하면 `내`처럼 약한 한 단어만 겹쳐도 관련 없는 조문이 올라왔다. Precision@5 `0.213`, Recall@5 `0.611`으로 기준선보다 낮았다. |
| Kiwi 형태소 분석 + BM25 | 미채택. `은행이 → 은행`처럼 한국어 조사를 분리할 수 있었지만, 이번 개발 문항에서는 추가 의존성에 비해 평균 성능 이득이 없었다. |
| 2글자 단위 BM25 + Dense 우선 순위 결합 | 채택. `예금`, `보호`, `파산`처럼 핵심 표현의 일부를 비교해 조사 변화에 덜 민감했다. BM25 비중을 낮춰 의미 검색 결과를 뒤집지 않도록 했다. |
| 3·4글자 단위 BM25 | 미채택. 낮은 비중에서는 2글자 방식과 같은 평균 Recall을 보였다. 더 단순한 2글자 방식을 유지했다. |

BM25는 점수를 그대로 합치지 않고, 각 검색 결과에서 **몇 번째로 나왔는지**를 합쳤다.
이 방식은 Reciprocal Rank Fusion(RRF)이며, 여기서는 “두 목록의 순위를 부드럽게
합치는 방법” 정도로 이해하면 된다.

## 3. 적용

[`src/chatbot/retriever.py`](../../../src/chatbot/retriever.py)에서 다음 규칙을 적용했다.

1. 질문과 법령 청크를 유니코드 NFC로 통일하고 소문자로 바꾼다.
2. 한글·영문·숫자 단어를 2글자 조각으로 나눠 BM25에 전달한다.
3. 질문과 2글자 조각이 한 개만 겹치는 청크는 제외한다. `내`처럼 우연히 겹친 단어가
   결과를 흔드는 것을 막기 위한 최소 조건이다.
4. Dense와 BM25에서 각각 최대 50개 후보를 가져온다.
5. RRF로 순위를 합치되 Dense 비중은 `1.0`, BM25 비중은 `0.1`로 둔다.
6. 같은 법령·조문은 하나로 정리한 뒤 최종 5개 조문을 반환한다.

현재 법령 청크는 322개라 BM25 목록을 요청마다 만드는 비용이 작다. 문서가 크게
늘어나면 BM25 인덱스를 미리 만들어 재사용하는 구조를 다시 검토해야 한다.

## 4. 비교 결과

| 방식 | Precision@5 | Recall@5 | 판단 |
| --- | ---: | ---: | --- |
| Dense Search | 0.280 | 0.711 | 기준선 |
| 단어 단위 BM25, 같은 비중 결합 | 0.213 | 0.611 | 미채택 |
| **2글자 BM25, 보조 비중 0.1** | **0.280** | **0.744** | 채택 |

정밀도 평균은 유지됐고, 필요한 조문을 5개 안에서 찾는 비율만 소폭 올랐다. 따라서
“모든 질문이 더 좋아졌다”는 결론은 아니다.

### 대표 사례

- **개선된 사례**: 예금 보호 한도 질문에서 `예금자보호법 시행령 제18조`가 상위 5개에
  포함되어 `1억원` 근거를 전달할 수 있게 됐다.
- **주의 사례**: 개발 문항 A10은 정밀도가 `0.8 → 0.6`으로 낮아졌다. Recall은 그대로
  `1.0`이었다. 관련 조문을 더 가져오는 대신 상위 5개 중 일부가 덜 직접적인 조문으로
  바뀔 수 있음을 보여 준다.
- **시간**: 322개 청크, 로컬 워밍 상태에서 5회 평균 Dense Search는 약 `0.029초`,
  Hybrid Search는 약 `0.067초`였다. 이번 환경에서는 약 `0.038초`가 늘었다. 이는
  운영 환경 성능 보장이 아닌 작은 로컬 POC 측정이다.

## 5. 결정과 남은 한계

이번 POC에서는 **Dense Search를 중심으로 두고 2글자 BM25를 약하게 보조하는 방식**을
채택한다. 정확한 법률 표현을 보완하면서도, 단어 일치만으로 결과가 크게 바뀌는 위험을
줄이는 선택이다.

이번 실험에서 `5,000만원`이라는 잘못된 최종 답변도 확인됐다. 법령 XML의 현행 내용은
`1억원`이었고 검색 도구 결과에도 `5,000만원` 근거는 없었다. 이는 Hybrid Search가
직접 만든 오류가 아니라, Agent가 도구 결과 밖의 숫자를 답변에 쓴 생성 단계 오류였다.
따라서 BM25 도입을 “금융 답변이 안전해졌다”는 근거로 사용하면 안 된다.

다음 검증에서는 다음을 분리해 진행한다.

1. 이번 15개 개발 문항과 분리된 고정 문항으로 검색 회귀 평가
2. Agent가 금액·시행일을 답할 때 검색 근거 안에 같은 값이 있는지 확인하는 안전 장치
3. 문서 수가 늘어난 뒤 BM25 인덱스 재사용 또는 Reranker의 비용·효과 비교

BM25의 기본 사용 방식은 호출하는 쪽에서 같은 전처리를 문서와 질문에 적용하는 것이다.
관련 구현 방식은 [rank-bm25 문서](https://github.com/dorianbrown/rank_bm25/blob/master/README.md)를
참고했다. 현행 보호 한도는 [금융위원회 안내](https://www.fsc.go.kr/no010101/85200)와
[국가법령정보센터 개정 이력](https://www.law.go.kr/LSW/lsRvsDocListP.do?chrClsCd=010202&lsId=004223&lsRvsGubun=all)으로 다시 확인했다.
