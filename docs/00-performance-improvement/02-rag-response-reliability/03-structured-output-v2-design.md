# RAG Structured Output v2 설계

- 작성일: 2026-07-27
- 상태: POC 구현과 실제 검색·Ollama 대표 질문 확인, Streamlit 수동 확인과 24문항 비교 평가 전
- 적용 대상: 기본 Ollama backend의 법령 RAG

## 관찰

기존 RAG는 Prompt가 답변 형식과 근거 사용을 모두 지시하고 `StrOutputParser`가
모델 문자열을 그대로 반환했다. 간결화 Prompt 실험에서는 답변 길이와 생성 시간이
줄었지만, `확인할 수 없습니다`가 반대 의미로 생성되고 필요한 조건과 상담 설명도
함께 사라졌다.

또한 LangChain의 system·human 메시지는 문자열 하나로 합쳐져 Ollama의 user
메시지 한 개로 전송되고 있었다. 따라서 기존 실험은 역할별 chat 입력과 schema
제약을 사용한 결과가 아니었다.

상세 사례와 수치는
[간결화 Prompt 실험과 미채택 결정](02-conciseness-prompt-experiment.md)에 보존한다.

## 선택

| 방법 | 판단 |
| --- | --- |
| Prompt만 다시 수정 | 표현은 유도하지만 필드와 상태를 보장하지 못함 |
| JSON 예시와 문자열 parser | 자유 생성 뒤 오류를 발견하는 방식 |
| `ChatOllama.with_structured_output()` | Agent Tool 연결 단계에서 장점이 더 큼 |
| Ollama JSON Schema + Pydantic | 현재 HTTP 경계를 유지하며 생성과 검증에 schema 사용 |

이번 POC는 Ollama `/api/chat`의 `format`에 Pydantic JSON Schema를 전달한다.
LangChain 메시지 역할을 보존하고, 모델 결과는 다시 Pydantic으로 검증한다.
법령 출처는 모델이 직접 작성하지 않고 검색 조문에 부여한 `S1`~`S5` 중에서
선택하게 한다.

Structured Output은 JSON 모양을 안정시키지만 법률 내용의 정확성을 보장하지 않는다.
그래서 답변 가능 여부와 근거 ID 조합은 Python 코드가 다시 확인하고, 존재하지 않는
근거를 선택하면 근거 부족 안내로 안전하게 닫는다.

첫 구현은 `answered`·`partial`·`insufficient` 상태와 `limitations`까지 모델이
판단하게 했다. 그러나 Qwen 4B가 상태 구분, 상담 답변, 출처 선택, 한계 작성과 금지
규칙을 동시에 처리해야 했다. 특히 `partial`은 답할 수 있는 부분과 없는 부분을
모델이 다시 판단해야 해 POC의 직접 검증 범위를 넘어갔다.

그래서 현재 법령 RAG에 꼭 필요한 판단만 남겼다. 질문에 직접 답하는 근거가 있는지는
`can_answer` 하나로 구분하고, 근거가 없을 때의 고객 안내는 코드가 담당한다.

## 적용

구조화 모델 응답은 세 필드만 사용한다.

```text
can_answer  제공된 근거로 질문에 직접 답할 수 있는지
answer      답할 수 있을 때의 쉬운 한국어 존댓말 설명
source_ids  답변을 직접 뒷받침하는 검색 근거 ID
```

실행 흐름은 다음과 같다.

```text
검색 조문에 S1~S5 부여
  → system·user 메시지를 역할별로 Ollama에 전달
  → JSON Schema로 생성 형식 제약
  → Pydantic 형식 검증
  → 답변 가능 여부·근거 ID 조합 검증
  → 실제 검색 메타데이터로 근거 법령 표시
  → 상담형 문자열 반환
```

`can_answer=false`이거나 의미 검증에 실패하면 모델 문장을 표시하지 않고
근거 부족 안내를 코드에서 반환한다. 안내는 단순히 조문이 없다고 끝내지 않고,
정확한 답변이 어려운 이유, 추측하지 않는다는 원칙, 개별 상품의 공식 자료를 다시
확인하는 방법을 고객 관점의 세 문장으로 제공한다.

구조화 JSON은 완성된 뒤에야 검증할 수 있으므로 현재 스트리밍 endpoint도 검증이
끝난 최종 답변을 한 조각으로 전달한다. UI 계약은 유지되지만 토큰이 생성되는 즉시
보이던 동작은 잠시 사용하지 않는다.

현재 Hugging Face backend에는 Ollama의 native JSON Schema와 같은 제약이 없다.
이번 v2 검증과 비교 평가는 기본 Ollama backend만 대상으로 한다.

## 결과와 비교 계획

단위 테스트에서는 역할별 메시지와 schema 전달, 잘못된 JSON 거부, 존재하지 않는
근거 ID 차단, 근거 부족 고정 안내를 확인한다. 실제 Qwen 호출에서는 JSON schema
준수를 확인했고, 단순 지시만 사용했을 때 존재하지 않는 근거 ID를 만들 수 있어
코드 검증이 필요하다는 점도 확인했다.

실제 정상 근거 한 건에서는 `can_answer=true`와 유효한 근거 ID를 반환해 코드가 실제
법령명·조문·시행일을 표시했다. 다만 모델은 answer 안에서도 법령 출처를 한 번
반복했다. 출처 표현 금지를 Prompt와 schema 설명에 더 강하게 반복했을 때는 답변이
오히려 길어지고 근거 본문에 없는 목적 설명이 추가되어 해당 변경을 되돌렸다.
Structured Output이 자연어 내용과 말투의 정확성까지 해결하지 않는다는 관찰이며,
서버 UI와 24문항 비교가 필요한 이유다.

출력 계약과 Prompt를 단순화한 뒤 실제 Qwen 호출을 다시 확인했다. 근거 한 건을
전달한 보호 한도 질문에는 `예금자보호는 1억 원까지 받을 수 있습니다.`라고 답하고
`S1`만 선택했다. 검색 근거가 없는 상품 추천 질문에는 모델이 만든 문장 대신 코드의
고객 안내가 반환됐다.

실제 벡터 검색 `top 5`까지 포함한 경로에서는 질문에 따라 차이가 분명했다.

| 질문 | 검색·생성 결과 | 해석 |
| --- | --- | --- |
| 금융상품 광고 규제 | 관련 법률·시행령 5개를 선택하고 존댓말과 번호 목록으로 설명 | 근거가 충분하면 상담형 답변과 실제 출처 렌더링 동작 |
| 은행 파산 시 보호 한도 | 정답 조문이 `top 5`에 없어 근거 부족 안내 | 알려진 금액을 추측하지 않았지만 검색 품질이 최종 답변을 제한 |
| 최고 금리 적금 추천 | 상품 정보가 연결되지 않아 근거 부족 안내 | 현재 법령 RAG와 이후 Finlife Agent의 책임 경계 확인 |

광고 규제 답변은 충분한 설명을 생성했으므로 정상 답변을 더 길게 만들기 위해 system
Prompt를 다시 복잡하게 만들지 않았다. 반대로 보호 한도 질문의 실패는 Prompt를
늘려 해결할 문제가 아니다. 시행령 제18조와 법 제32조가 검색되지 않은 상태에서
모델이 답하게 하면 근거 없는 답변이 되므로, 후속 개선 대상은 검색 단계다.

이 세 사례는 정상·안전 경로 확인일 뿐 전체 품질 개선 결과는 아니다.

Streamlit UI에서 표현과 줄바꿈을 수동 확인한 뒤 기존 24문항으로 다음 값을
비교한다.

| 비교 항목 | 확인 목적 |
| --- | --- |
| schema 검증 성공률 | 출력 형식 안정성 |
| 근거 ID 유효성 | 검색되지 않은 법령 인용 차단 |
| 필수·금지 주장 | 필요한 설명 유지와 근거 밖 주장 확인 |
| Faithfulness | 검색 문맥 충실도 |
| 답변 길이·생성 시간 | 구조화로 생긴 비용과 품질의 균형 |
| 상담 말투 수동 검토 | 금융 안내로 사용할 수 있는 설명 수준 |

이 비교 전에는 Structured Output v2를 성능 개선 완료로 기록하지 않는다.
