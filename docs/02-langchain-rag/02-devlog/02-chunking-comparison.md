# 청킹 비교 — 조문 경계를 지킬 것인가

- 작성일: 2026-07-06
- 현재 상태: 조문 보존 + 1000자/overlap 100 구현 완료

## 해결하려던 문제

검색에서는 청크 하나가 벡터 하나가 된다. 조문 전체를 한 청크로 두면 출처는
명확하지만 긴 조문의 내용이 한 벡터에 섞인다. 반대로 너무 잘게 자르면 검색은
정밀해질 수 있지만 문맥과 인용 단위가 흩어진다.

파싱 결과는 260개 조문이다. 전체가 삭제된 스텁 2건을 제외한 258개 조문 중
216개(84%)는 1,000자 이하였고, 42개만 1,000자를 넘었다. 최대 길이는
4,753자였다.

## 비교

모든 후보는 조문 단위로 파싱된 같은 입력을 사용하고 조문 경계를 넘지 않는다.

| 후보 | 방식 | 청크 수 | 중앙값 | 최대 | 분할 조문 |
| --- | --- | ---: | ---: | ---: | ---: |
| A | 조문 전체 유지 | 258 | 371자 | 4,753자 | 0 |
| B | 1,000자 / overlap 100 | 322 | 403자 | 1,000자 | 42개 |
| C | 500자 / overlap 50 | 460 | 384.5자 | 500자 | 95개 |

A는 긴 조문의 검색 표현이 흐려질 수 있고, C는 95개 조문을 여러 조각으로
나눈다. 검색 품질을 측정하기 전부터 대부분의 조문을 잘게 나눌 근거가 없었기
때문에 B를 선택했다.

## 현재 구현

[`chunking.py`](../../../src/chatbot/chunking.py)의 `chunk_articles()`는 다음
규칙을 사용한다.

- 1,000자 이하 조문은 그대로 유지
- 긴 조문만 `RecursiveCharacterTextSplitter`로 내부 분할
- 자식 청크에 법령명·조문번호·제목·시행일과 `chunk_index` 복사
- 각 청크 앞에 `[법령명 조문번호 | 제목]` 출처 헤더 추가
- 전체가 삭제된 조문 2건 제외, 부분 삭제된 살아있는 조문 유지

테스트는 최대 본문 길이, 조문 경계, 자식 메타데이터, 삭제 스텁 처리를
확인한다. KURE-v1 토크나이저로 측정한 최장 청크는 608 token이라 모델의
8,192 token 입력 한도 안에 들어간다. 이는 입력 한도와 호환된다는 뜻이지,
현재 청킹이 검색 품질상 최적이라는 뜻은 아니다.

## 배운 점

- 법령의 조문 구조를 먼저 보존하면 출처 메타데이터가 모호해지지 않는다.
- corpus 대부분은 건드리지 않고 긴 꼬리만 처리하는 방식으로 시작할 수 있다.
- 문자 길이 제한과 모델 token 제한은 다르므로 임베딩 모델을 정한 뒤 다시
  확인해야 한다.
- 최종 청킹 품질은 길이 통계가 아니라 실제 retrieval 평가로 판단해야 한다.
