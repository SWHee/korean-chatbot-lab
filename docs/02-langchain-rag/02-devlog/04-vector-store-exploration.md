# Chroma에 저장하고 검색한 결과

- 작성일: 2026-07-06
- 현재 상태: 322개 법령 청크 인덱싱·검색 검증 완료

## 확인하려던 것

임베딩 벡터만 저장하면 검색 결과가 어느 법령의 몇 조인지 답변에 표시하기
어렵다. Chroma가 청크 본문과 출처 메타데이터를 함께 저장하고, 현재 검색
결과가 임베딩 비교 실험과 일치하는지 확인했다.

## 현재 구현

[`build_index.py`](../../../scripts/build_index.py)는 다음 순서로 실행된다.

```text
법령 XML → 조문 파싱 → 청킹 → KURE-v1 임베딩 → Chroma 저장
```

현재 `statutes` 컬렉션에는 청크 322개가 있고, 각 레코드는 다음 정보를 가진다.

- 청크 ID: `법령명|조문번호|청크순번`
- 청크 본문
- 1024차원 정규화 벡터
- 법령명, 조문번호, 제목, 시행일, 청크 순번

인덱스는 `data/index/chroma/`에 생성되지만 파생물이므로 Git에는 넣지 않는다.
같은 스크립트로 다시 만들 수 있다.

[`vectorstore.py`](../../../src/chatbot/vectorstore.py)는 저장된 컬렉션을 열고,
질의 벡터에 가까운 청크를 본문·메타데이터·유사도와 함께 반환한다. 아직
FastAPI나 생성 모델과 연결하지 않았으므로 현재 구현 범위는 검색까지다.

## 검색 검증

[`verify_index.py`](../../../scripts/verify_index.py)로 15개 평가 질문을 실행했다.

- Chroma와 전체 벡터를 직접 비교한 검색의 top-5 조문: 15/15 일치
- 정답 조문이 Chroma top-5에 포함된 질문: 12/15

이 결과는 현재 작은 인덱스에서 두 검색 결과가 같았다는 뜻이다. corpus가
커지거나 Chroma 설정이 바뀌면 다시 확인해야 한다.

개별 검색을 살펴보면 한계도 있었다. A1 질문에서는 예금자보호법 제1조처럼
핵심 단어가 많은 목적 조문이 정답보다 높게 나왔다. 또한 질문 하나의 유사도
분포만으로 고정 임계값을 정하기에는 근거가 부족했다. 현재는 top-k 순위를
사용하고, 범위 밖 질문의 거절은 이후 RAG 답변 단계에서 평가한다.

## 이후에 검토할 검색 기능

Chroma에서 법령명 metadata filter와 문서의 문자열 포함 조건을 사용할 수
있다는 점을 확인했다. 특정 법령을 이미 아는 질문이나 키워드 검색을 보완할 때
후보가 될 수 있지만, 현재 `search()` 경로에는 적용하지 않았다. 기본 벡터 검색
기준선을 먼저 만든 뒤 실제 개선 여부를 평가한다.

## 배운 점

- 벡터와 함께 원문·출처를 저장하면 검색 결과를 바로 인용 자료로 사용할 수
  있다.
- 벡터 DB를 선택한 것과 검색 품질이 확보된 것은 별개라 평가 질문으로 확인해야
  한다.
- 검색은 관련성이 낮아도 항상 결과를 반환하므로, 범위 판단은 RAG의 상위
  단계에서 따로 설계해야 한다.
- 내부 파일 구조보다 현재 코드가 넣고 꺼내는 데이터 계약을 먼저 이해하는 것이
  이 PoC 단계에 적합하다.
