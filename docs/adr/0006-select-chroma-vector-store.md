# ADR 0006. 벡터스토어로 Chroma를 선택한다

- 상태: Proposed
- 날짜: 2026-07-06
- 구현 상태: 인덱싱 완료 (청크 322개)

## 배경

KURE-v1 임베딩(ADR 0005) 1024차원 벡터 322개를 저장·검색할 벡터스토어가
필요하다. 이 규모에서는 어떤 후보든 검색이 밀리초에 끝나므로 성능은
결정 기준이 아니다. 실질 기준은 네 가지다.

- 답변이 법령명·조문번호·시행일을 인용해야 하므로 메타데이터를 1급으로
  저장·반환할 수 있는가
- 서버 프로세스 없이 로컬 파일로 영속되고, clone 후 스크립트 1회로
  재생성 가능한가
- 다음 단계(벡터스토어 내부 탐색, LangChain retriever 연결)와 자연스럽게
  이어지는가
- 의존성과 운영 부담이 프로젝트 규모에 맞는가

## 고려한 선택지

1. FAISS — 벡터 인덱스 라이브러리. 정확한(flat) 검색과 최소 의존성이
   장점이나 벡터와 정수 ID만 저장한다. 원문·메타데이터는 별도
   저장소(LangChain 래퍼는 pickle docstore)를 직접 관리해야 한다.
2. Chroma — 임베디드 벡터 DB. 문서·메타데이터·벡터를 함께 저장하고
   SQLite 기반 파일로 persist된다. 검색은 HNSW 근사.
3. Qdrant — 서버형(로컬 모드 존재). 필터·페이로드 기능이 강하지만 벡터
   322개에 별도 서버는 과하다. Ollama 도입 때와 달리 해결할 문제가 없다.
4. Milvus·Weaviate 등 서버형 — 같은 이유로 제외.

## 결정

Chroma(chromadb, 임베디드)를 벡터스토어로 선택한다. 코사인 공간의 단일
컬렉션 `statutes`에 청크 본문과 메타데이터(법령명·조문번호·제목·시행일·
청크 순번)를 함께 저장한다.

인덱스는 `data/index/chroma/`에 persist하되 파생물이므로 커밋하지
않고(.gitignore), `scripts/build_index.py`(멱등, 재실행 시 재생성)만
커밋한다.

## 결정 이유

- 메타데이터가 검색 결과에 그대로 붙어 나와, 근거 인용 요구를 별도
  저장소 없이 충족한다. FAISS는 이 절반을 직접 만들어야 한다.
- SQLite 기반 파일이라 다음 세션(벡터스토어 내부 탐색)에서 저장 구조를
  직접 열어볼 수 있다.
- HNSW 근사 검색의 손실을 실측으로 확인했다: 평가 질문 15개 전부에서
  top-5 조문이 브루트포스 정확 검색과 완전히 일치했고, Hit@5
  12/15(0.800)로 임베딩 선정 실험과 동일하게 재현됐다. 이 규모에서 근사
  손실은 관찰되지 않는다.
- LangChain에 공식 Chroma 통합이 있어 retriever 연결(다음 단계)이 쉽다.
  다만 현재 접근 경계는 프로젝트 소유의 `vectorstore.py`로 유지한다.

## 감수하는 단점

- HNSW는 근사 알고리즘이므로 corpus가 커지면 정확 검색과의 일치를
  재검증해야 한다. 322개에서의 무손실이 일반화되지는 않는다.
- chromadb는 FAISS보다 무거운 의존성이다(내장 서버 등 미사용 기능 포함).
- 임베디드 구조라 여러 프로세스가 동시에 쓰는 시나리오에 제약이 있다.
  현재는 인덱싱(배치 1회)과 읽기(서빙)뿐이라 문제가 없다.
- flat 인덱스 대비 인덱스 자료구조를 직접 다루는 학습은 얕아진다. 필요 시
  다음 세션의 내부 탐색에서 보완한다.

## 검증 계획

다음 세션에서 persist된 파일 구조와 저장된 벡터·메타데이터를 직접
탐색해 기록한다. 전체 검색 기준선은 평가 질문 전체 실행 단계에서
측정한다.
