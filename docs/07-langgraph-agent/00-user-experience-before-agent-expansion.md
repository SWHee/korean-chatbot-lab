# Agent 확장 전 사용자 경험 점검

- 확인일: 2026-08-02
- 상태: 문제 확인, 검색 개선 전

## 왜 지금 기록하는가

Agent 기능을 늘리는 것보다 사용자가 질문하고 답을 이해하는 경험이 프로젝트의
목적에 더 가깝다. 검색 개선을 미뤄 둔 상태라도, 현재 사용자가 어디서 막히는지는
Agent 설계의 기준으로 남겨야 한다.

서버를 다시 실행한 뒤 개발자가 처음 쓰는 사용자처럼 질문했다. 화면은 깔끔하고
지원 범위도 분명해 보였지만, 표현이 조금만 달라져도 같은 근거 부족 안내가 반복됐다.

## 실제로 겪은 흐름

| 입력 | 결과 | 사용자에게 보이는 문제 |
| --- | --- | --- |
| 은행이 파산하면 예금은 얼마까지 보호되는지 질문 | 정답 조문을 찾지 못함 | 일반적인 질문인데 답하지 못함 |
| `예금자보호법` | 법의 목적 설명 성공 | 짧은 법률명도 되는 것으로 기대하게 됨 |
| `금융소비자보호법` | 근거 부족 | UI에 표시된 키워드인데 실패 |
| `금융소비자보호범` | 근거 부족 | 흔한 오타를 이해하거나 되묻지 못함 |
| `금융소비자보호법이 뭐냐고` | 제1조를 찾아 설명 성공 | 조사와 의도 표현 하나로 결과가 달라짐 |

안전한 `can_answer=false` 판단은 근거 없는 답변을 막았다. 문제는 질문이 모호한지,
오타인지, 검색이 정답 조문을 놓쳤는지를 구분하지 않고 모두 같은 안내로 끝낸다는
점이다. 사용자에게는 안전장치보다 대화를 이해하지 못하는 챗봇으로 보인다.

## 왜 이런 경험이 생겼는가

현재 서비스 경로는 사용자의 문장을 그대로 임베딩해 벡터 검색한다. 검색 전 오타
교정, 법률 약칭 변환, 질문 의도 보완과 키워드 검색은 아직 없다. Prompt와 Claude는
검색 이후에 실행되므로 앞에서 놓친 조문을 근거 있게 되살릴 수 없다.

질문 분석 Node도 아직 실제 FastAPI RAG 경로에 연결되지 않았다. 따라서 Agent 확장
코드를 만들고 있어도 현재 UI는 기존 `retrieve → generate`만 사용한다.

## UI와 기능의 약속 불일치

UI는 `금융소비자보호법`을 지원 키워드로 표시한다. 실제 corpus의 공식 명칭은
`금융소비자 보호에 관한 법률`이며 backend에는 두 표현을 연결하는 처리가 없다.

약칭은 사용자에게 익숙하므로 UI에서 쓰지 못할 단어는 아니다. 다만 약칭을 보여주면
backend도 약칭과 예상 가능한 오타를 안정적으로 처리해야 한다. 그렇지 않으면 처음
보는 사용자는 화면이 약속한 질문조차 지원하지 않는다고 느낀다.

## Agent 작업에 반영할 기준

- 정상 문장뿐 아니라 약칭·오타·짧은 질문으로 직접 확인
- `clarify`, 오타 확인, 검색 근거 부족과 범위 밖 안내를 서로 구분
- UI에 표시한 예시와 키워드는 실제 backend 동작으로 검증
- 새 Node 수보다 사용자가 답에 도달하는 전체 경로를 완료 조건으로 사용
- 검색 개선 전에는 Agent가 검색 한계를 자동으로 해결한다고 표현하지 않음

검색 개선 후보와 적용 순서는
[법령 검색 견고성 개선 지도](../00-performance-improvement/04-retrieval-robustness/README.md)에 정리한다.
