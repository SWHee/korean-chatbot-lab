# RAG 응답 시간 측정 계획

- 작성일: 2026-07-23

현재 RAG는 로컬 Qwen3 모델로 답변을 만들고, Streamlit에서 생성되는 문장을
순서대로 보여줍니다. 기능은 정상적으로 동작했지만 LangSmith에서 확인한 전체 실행
시간은 사용자용 챗봇으로 사용하기에 길다고 느꼈습니다.

그렇다고 바로 모델이나 설정을 바꾸지는 않기로 했습니다. 먼저 LangGraph 전환과
Agent 확장을 평가한 뒤, 같은 조건에서 응답 시간을 나누어 측정하고 한 번에 한
요소만 바꿔보려고 합니다.

## 현재 확인한 상태

LangChain v1의 24문항 기준선에서 RAG 실행 시간은 다음과 같습니다.

| 항목 | 시간 |
| --- | ---: |
| 평균 | 18.75초 |
| 최소 | 10.84초 |
| 최대 | 29.21초 |

LangGraph trace 한 건을 확인해보니 전체 15.79초 중 검색 Node는 0.88초, 생성
Node는 14.56초였습니다. 적어도 이 질문에서는 검색보다 생성이 대부분의 시간을
차지했습니다. 다만 한 질문만 보고 모든 질문의 병목이 같다고 단정하지는 않았습니다.

LangGraph 전환 후 같은 24문항을 실행했을 때는 평균 18.35초가 나왔습니다.
LangChain 기준선의 18.75초보다 0.40초 짧았습니다. 하지만 두 구조 모두 같은 검색
함수와 로컬 생성 모델을 사용하고, 답변 길이와 모델 적재 상태도 따로 고정하지
않았습니다. 이 결과만으로 LangGraph가 응답을 빠르게 만들었다고 보기는 어려웠습니다.

현재 생성 모델 설정은 다음과 같습니다.

- 모델: `qwen3:4b-instruct-2507-q4_K_M`
- 파라미터: 4B
- 양자화: Q4_K_M
- Ollama 적재 크기: 약 3.17GB
- context 길이: 4,096
- 생성 상한: 1,024토큰
- 검색 문맥: 조문 단위 상위 5개

## 나누어 볼 시간

전체 실행 시간만 보면 사용자가 어느 단계에서 오래 기다렸는지 알기 어렵다는 것을
알게 되었습니다. 이후에는 다음 시간을 나누어 확인할 예정입니다.

| 지표 | 의미 | 확인 목적 |
| --- | --- | --- |
| 검색 시간 | 질문 임베딩부터 조문 검색 완료까지 | Retriever 병목 확인 |
| 첫 토큰 시간 | 요청부터 첫 글자가 화면에 나타날 때까지 | 사용자가 처음 기다리는 시간 확인 |
| 전체 응답 시간 | 요청부터 마지막 글자까지 | 한 질문의 총 처리 시간 확인 |
| 모델 적재 시간 | Ollama 모델을 메모리에 올리는 시간 | 첫 요청과 유휴 후 지연 확인 |
| prompt 처리 시간 | 모델이 질문과 법령 문맥을 읽는 시간 | 검색 문맥 길이의 영향 확인 |
| 생성 시간 | 첫 토큰부터 마지막 토큰까지 | 답변 길이와 생성 속도 확인 |
| prompt 토큰 수 | 모델이 입력으로 읽은 토큰 수 | 문맥 축소 필요성 판단 |
| 생성 토큰 수 | 모델이 출력한 토큰 수 | 생성 상한과 답변 길이 판단 |

LangSmith에서는 Graph 전체와 Node별 실행 시간을 확인할 수 있습니다. Ollama도
마지막 응답 조각에 모델 적재, prompt 처리와 생성 토큰 관련 수치를 제공합니다.
하지만 현재 Generator는 이 값을 보존하지 않습니다. 실제 측정을 시작할 때 필요한
값만 작게 연결하려고 합니다.

## 비교 조건

변경 전후를 비교할 때는 다음 조건을 같게 유지해야 합니다.

- 질문과 Dataset
- 법령 corpus snapshot
- 임베딩 모델과 Chroma index
- 생성 모델과 양자화
- RAG prompt
- `top_k`
- 콜드 실행인지 웜 실행인지

서버 시작 후 첫 실행과 이미 모델이 적재된 실행을 섞으면 비교가 흐려질 수 있습니다.
대표 질문을 정한 뒤 콜드 실행 1회와 웜 실행 여러 회를 구분하고, 평균뿐 아니라 첫
토큰 시간과 출력 길이도 함께 기록할 예정입니다.

## 콜드 상태와 웜 상태

콜드 상태와 웜 상태라는 표현도 이번에 처음 접했습니다. 콜드 상태는 요청한 모델이
아직 실행 메모리에 적재되지 않은 상태이고, 웜 상태는 앞선 요청으로 모델이 메모리에
남아 있는 상태입니다.

FastAPI 서버를 시작할 때 현재 코드는 `OllamaGenerator` 객체만 만듭니다. 이 단계에서는
Ollama `/api/chat`을 호출하지 않으므로 Qwen 모델을 미리 적재하지 않습니다.
Streamlit 서버도 FastAPI를 호출하기 전에는 모델 적재에 영향을 주지 않습니다. 저는
서버를 켜면 모델도 바로 준비되는 줄 알았지만, 실제로는 첫 질문이 들어와 생성 API를
호출할 때 모델이 적재됩니다.

Ollama는 별도 설정이 없으면 마지막 요청 이후 모델을 기본 5분간 메모리에 유지합니다.
따라서 첫 요청이나 오래 쉰 뒤의 요청에는 모델 적재 시간이 포함될 수 있고, 바로
이어지는 요청은 그 시간이 줄어들 수 있습니다. 현재 생성기는 `keep_alive`를
지정하거나 응답의 `load_duration`을 저장하지 않습니다. 그래서 이번 24문항 평가의
시간 차이를 콜드·웜 상태만으로 설명할 수는 없었습니다.

추후에는 다음 순서로 두 상태를 직접 구분해볼 예정입니다.

1. `ollama stop <model>`로 모델을 메모리에서 내린 뒤 첫 요청 측정
2. `ollama ps`로 모델 적재 여부 확인
3. 같은 질문을 바로 다시 실행해 웜 요청 측정
4. Ollama 응답의 `load_duration`을 함께 기록

참고:

- [Ollama FAQ: 모델 사전 적재와 keep_alive](https://docs.ollama.com/faq)
- [Ollama API usage metrics](https://docs.ollama.com/api/usage)

## 설정별로 예상되는 영향

| 변경 후보 | 주로 영향을 받는 부분 | 확인할 부작용 |
| --- | --- | --- |
| 모델 사전 적재·`keep_alive` | 첫 요청과 유휴 후 지연 | 메모리·배터리 상시 사용 |
| 간결한 답변 지시·생성 상한 축소 | 생성 시간 | 필요한 설명 누락 |
| 모델에 전달하는 조문 수 축소 | prompt 처리 시간 | 정답 조문 누락 |
| 검색 또는 reranking 개선 | 검색 품질과 전달 문맥 | 추가 처리 시간 |
| 생성 모델·실행 backend 변경 | prompt 처리와 생성 속도 | 답변 품질과 비교 기준 변경 |

`top_k`와 검색 방식을 바꾸면 검색 시간 자체보다 모델에 전달되는 문맥 길이가 달라질
수 있습니다. 따라서 검색 설정은 속도만 보고 줄이지 않고 Precision·Recall과 답변
품질을 함께 비교합니다.

## 이후 작업 순서

1. 같은 Dataset으로 LangGraph 전환 전후 평가
2. Finlife API와 조건 분기를 추가한 Agent 평가
3. 대표 질문과 측정 조건 확정
4. 첫 토큰·전체 응답·Ollama 세부 시간 기록
5. 가장 큰 병목 하나 선택
6. 설정 하나만 변경해 같은 질문으로 재측정
7. 속도와 RAG 품질 변화를 함께 기록

현재 단계에서는 “응답 시간이 길다”는 문제와 앞으로 측정할 항목까지만 기록합니다.
실제 최적화는 Graph와 Agent의 기능 기준선을 남긴 뒤 별도 작업으로 진행할
예정입니다.
