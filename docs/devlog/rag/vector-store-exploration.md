# 벡터스토어 들여다보기 — Chroma는 내 데이터를 어디에 어떻게 넣었나

- 작성일: 2026-07-06
- 상태: 인덱스(청크 322개) 내부 탐색 완료

## 시작점

벡터스토어를 골랐고(ADR 0006) 인덱싱도 끝났지만, "검색이 된다"와 "안에서
무슨 일이 일어나는지 안다"는 다르다. 다음 단계(retriever 연결)로 가기
전에 persist된 파일을 직접 열어 세 가지를 확인했다. 내 데이터가 어디에
저장됐는지, 벡터가 실제로 어떤 모습인지, 검색 외에 어떤 기능이
숨어있는지.

## 파일 구조 — DB 하나와 바이너리 몇 개

`data/index/chroma/`의 실체는 단출하다.

- `chroma.sqlite3` (4.8MB) — 본체. 원문, 메타데이터, 그리고 뜻밖에도
  벡터까지 여기 있었다(아래 반전 참고).
- `<UUID>/` 디렉터리 — HNSW 인덱스 바이너리(`data_level0.bin` 448KB,
  `link_lists.bin` 0B 등). UUID는 sqlite의 `segments` 테이블에 있는 vector
  segment ID와 일치한다.

sqlite라서 표준 도구로 바로 열린다. `sqlite3 chroma.sqlite3 ".tables"`를
치면 테이블 20여 개가 나오는데, 핵심은 `embeddings`(322행, ID 매핑),
`embedding_metadata`(1,932행 = 322 × 6), `embeddings_queue`(322행),
그리고 `embedding_fulltext_search`(전문검색 인덱스)다.

재미있는 건 `embedding_metadata`다. 내가 넣은 메타데이터 5개(법령명,
조문번호, 제목, 시행일, 청크 순번)에 더해 `chroma:document`라는 키로
**청크 원문 자체도 key-value 행으로** 저장된다. "문서를 함께 저장하는
DB"의 실제 구현은 metadata 테이블의 예약 키였다.

## 계산이 안 맞는 파일 크기 — 설정 해석에서 한 번 틀렸다

계산이 안 맞는 지점이 하나 있었다. 벡터 원본 크기는 322개 × 1024차원 ×
4바이트 ≈ 1.3MB인데 `data_level0.bin`은 448KB뿐이고 `link_lists.bin`은
0바이트다. 벡터가 HNSW 파일에 다 들어있지 않다는 뜻이다.

`collection.configuration_json`의 HNSW 파라미터(`space=cosine,
ef_construction=100, ef_search=100, max_neighbors=16,
sync_threshold=1000`)에서 실마리를 찾았는데, 처음에는
"sync_threshold=1000 미만이라 HNSW가 아직 시작되지 않았고 검색은 큐를
순차 스캔한다"고 결론냈다. 교차 검증에서 틀렸다고 교정받았다. Chroma
문서 기준으로 두 설정의 역할은 이렇다.

- `batch_size`(기본 100): brute-force 버퍼가 이 크기에 도달하면 벡터를
  인메모리 HNSW 인덱스로 옮긴다
- `sync_threshold`(기본 1000): 인메모리 HNSW를 디스크에 저장하는 주기

즉 322개 중 대부분은 이미 인메모리 HNSW에 있고, 디스크 파일이 작은 것은
동기화 주기 문제다. `embeddings_queue`도 "HNSW에 안 들어간 벡터
목록"이 아니라 장애 복구용 WAL(write-ahead log)이다.

그래서 앞 세션 결과의 정확한 해석은 이렇게 제한된다. **현재 Chroma 검색
결과가 브루트포스와 15문항 전부 일치했지만, HNSW와 brute-force 버퍼가
혼합된 내부 실행 경로까지 이번 탐색으로 분리 검증한 것은 아니다.**
corpus가 커지면 일치 검증을 다시 한다(재현:
`scripts/verify_index.py`).

## 벡터 실물과 유사도의 스케일

`collection.get(include=["embeddings"])`로 벡터를 꺼내 보면 1024차원,
L2 norm이 전부 1.0이다(정규화 확인 — 동일성 원칙의 "정규화" 항목이
실제로 지켜졌는지 저장소에서 검증한 셈).

평가 질문 A1("은행이 파산하면 얼마까지 보호받나요?")으로 322개 청크
전체의 유사도 분포를 봤다. top1 0.627, 10위 0.536, 중앙값 0.442, 최하위
0.323. 두 가지가 보인다.

- **절대값의 범위가 좁다.** 최고와 최저 차이가 0.3밖에 안 된다. 적어도
  이 문항의 분포에서는 "유사도 0.5 이상만 채택" 같은 고정 임계값의
  근거가 부족하다 — 전체 평가 질문으로 분포를 측정한 뒤 판단할 문제고,
  그전까지는 순위(top-k)를 신호로 쓴다.
- **전역 top1이 예금자보호법 제1조(목적)다.** gold인 제32조가 아니다.
  목적 조문은 "예금자 보호"라는 핵심 어휘가 밀집해 있어 여러 질문에서
  상위로 끌려 나오는 잡음 패턴이 될 수 있다 — retriever 이후 단계에서
  기억해 둘 관찰이다.

## 검색 말고 숨어있던 기능 둘

- **메타데이터 필터**: `where={"law_name": "예금자보호법 시행령"}`을 걸면
  같은 질문에서 시행령 제18조(1억원 한도)가 top1으로 올라온다. 전역
  검색에서 10위였던 gold가 필터 하나로 1위가 되는 것 — 질문의 법령을
  아는 경우 강력한 보정 수단이다.
- **전문검색(FTS)**: 문서를 넣을 때 Chroma가 자동으로 전문검색 인덱스를
  만든다. `where_document={"$contains": "1억원"}`으로 정확히 4개 청크가
  나온다(예보법 §32, 시행령 §18, 금소법 §69, 금소법 시행령 §5). 벡터
  유사도와 키워드 매칭을 섞는 hybrid 검색의 재료가 이미 안에 있다.

## 배운 점

- 파일 크기와 테이블 행수만으로 내부 동작을 단정하면 틀린다. batch_size와
  sync_threshold처럼 이름이 비슷한 설정은 공식 문서에서 정확한 역할을
  확인해야 했다. "일치했다"는 관찰과 "왜 일치했나"는 해석을 분리하는
  훈련이 됐다.
- 유사도 절대값을 임계선으로 쓰려면 문항 하나가 아니라 전체 질문의
  분포 측정이 선행되어야 한다. 그전까지는 순위가 신호다.
- 저장 구조를 열어보면 다음 단계의 재료가 보인다. 메타데이터 필터와
  FTS는 문서만 읽었으면 지나쳤을 텐데, 내부를 뒤지다 발견해서 이후
  검색 품질 개선의 후보로 올려 둔다.
