# RAG 주제와 데이터를 고른 과정

- 작성일: 2026-07-06
- 상태: 주제·corpus 확정, 법령 원문 수집 전

## 시작점: 두 가지 데이터 스타일

FastAPI와 Ollama 서빙까지 끝내고 RAG로 넘어가면서, 코드보다 먼저 정해야
하는 것이 있었다. 무엇에 대해 답하는 챗봇인지, 그리고 근거 문서를 어디서
가져올 것인지다.

서칭을 시작할 때 데이터를 두 스타일로 나눠서 찾기로 했다.

- **스타일 1**: 원문을 내려받아 repo에 포함할 수 있는 데이터. clone만
  하면 인터넷 없이 인덱싱을 재현할 수 있다.
- **스타일 2**: 공식 API나 별도 다운로드 절차가 필요한 데이터.

두 스타일은 포트폴리오 관점에서 트레이드오프가 있었다. 스타일 1은
평가자가 clone 후 즉시 돌려볼 수 있고, 라이선스 출처를 명시하는 것
자체가 준법 어필이 된다. 대신 실무형 데이터 수집 경험 어필은 약하다.
스타일 2는 인증과 페이징을 다루는 ingest 코드가 실무 어필이 되지만,
평가자가 API 키를 발급받으면서까지 돌려보지는 않는다. 자칫 "코드만 있고
못 돌려보는 repo"가 될 위험이 있다.

## 전 도메인 서칭에서 걸러진 후보들

처음에는 도메인을 정하지 않고 스타일별로 후보를 조사했다.

스타일 1 쪽에서 라이선스를 통과한 후보는 이랬다.

- 법령·판례 원문 — 저작권법 제7조에 따라 헌법, 법률, 조약, 명령,
  조례·규칙 등은 저작권 보호를 받지 않는다. 원문 커밋과 청킹·가공이
  모두 자유롭다.
- 공공누리 제1유형 정부 문서 — "청년 정책 안내 챗봇" 방향
- 공유마당의 만료 저작물(현진건 「운수 좋은 날」 등) — "한국 근대문학 QA
  챗봇". 차별화는 되지만 실무 어필이 약하다.
- 한국어 위키백과 subset — CC BY-SA. 가능은 하지만 동일조건 변경허락
  관리가 따라온다.

반면 유명한 한국어 데이터셋은 대부분 라이선스에서 걸렸다.

- **KorQuAD 1.0**: CC BY-ND. ND(변경 금지) 조건이라 청킹·가공한 결과물을
  재배포할 수 없다. RAG는 문서를 잘라 저장하는 과정 자체가 가공이다.
- **AI Hub**: 데이터별로 이용 조건이 다르지만 공통적으로 제3자 재배포가
  제한된다. 원문을 repo에 넣을 수 없다.
- **모두의 말뭉치**: 제4유형 등 재배포 제한이 다수였다.

여기서 배운 것은, RAG 데이터는 "구할 수 있는가"보다 "repo에 넣고
가공해도 되는가"가 먼저라는 점이다. 공공기관 자료라고 전부 재배포
가능한 것이 아니었다.

이 단계의 첫 추천은 "전세·월세 계약 법률 도우미"였다. 주택임대차보호법과
판례를 corpus로 쓰는 생활법률 챗봇으로, 법령의 라이선스 장점을 그대로
활용하는 방향이었다.

## 금융으로 한정하다

여기서 방향을 조정했다. 도메인을 금융으로 한정하고, "신입 취준생이
면접에서 설명할 수 있는 난이도"라는 제약을 추가했다.

금융 안에서 다시 서칭하니 난이도 축이 먼저 갈렸다. 사업보고서나
자본시장법 같은 전문 금융은 도메인 지식이 과다해서, 면접에서 설명하지
못하면 오히려 역효과다. 예·적금과 예금자보호 같은 소비자 금융은 내가
직접 설명할 수 있다. 전자를 배제했다.

소비자 금융 안의 후보는 이랬다.

- 스타일 1: 금융 법령(예금자보호법, 금융소비자보호법, 전자금융거래법) /
  공공누리 1유형 금융 안내자료(금융꿀팁류 — 문서마다 유형 확인이 필요하고
  4유형이면 변경 금지)
- **한국은행 경제금융용어 700선**: 내용은 적합했지만 두 가지 이유로
  반려했다. 공공누리 표시가 없어 재배포 근거가 불명확했고, 국내 RAG
  튜토리얼의 단골 소재라 차별화가 약했다.
- 스타일 2: 금융감독원 금융상품한눈에 **finlife API** — 이메일로 즉시
  발급되고 약 140개 금융사의 예·적금 금리를 JSON으로 준다 / OPEN
  DART — 발급은 쉽지만 사업보고서 RAG는 난이도가 과해서 제외 / 한국은행
  ECOS — 통계 수치 위주라 문서 RAG보다 tool 용도

전자금융거래법은 초기 후보였지만 예·적금 이용자의 질문과 접점이 적어
최종 corpus에서는 제외했다.

## 법령이 두 스타일을 동시에 만족한다

정리하다 보니 법령의 위치가 특별했다. 저작권법 제7조 덕분에 원문을 repo에
동봉할 수 있고(스타일 1), 동시에 국가법령정보 공동활용
API(open.law.go.kr)가 구조화된 XML을 제공해서 수집 파이프라인도 만들 수
있다(스타일 2). 두 스타일을 동시에 만족하는 후보는 법령이 유일했다.
KorQuAD나 AI Hub, 뉴스 데이터로는 불가능한 조합이다.

RAG corpus로서의 특성도 좋았다.

- 조/항/호 구조가 표준화되어 있어 청킹 단위를 고민할 소재가 된다
- 개정이 이산적이고 시행일이 명시되어 변경 추적이 가능하다 —
  예금자보호 한도가 2025-09-01부터 5천만원에서 1억원으로 상향된 것이
  신선도 스토리의 좋은 예다

그래서 "금융 초보자를 위한 예·적금 어시스턴트"라는 큰 그림 아래, 이번
RAG 단계의 간판을 "예·적금 이용자를 위한 소비자보호 법령 Q&A"로 정했다.
정적인 법령은 RAG로, 변동하는 금리는 finlife tool로 — 이 분리가 이후
LangGraph 도입의 근거가 되고 MCP 확장 경로로도 이어진다.

## 법령이 상품 추천과 무슨 관련인가

그런데 여기서 스스로 의문이 생겼다. 예·적금 어시스턴트라면 사용자는
"금리 높은 적금 추천해줘"를 물을 텐데, 법령 corpus는 그 질문에 아무
도움이 안 된다.

고민 끝에 내린 결론은, 추천은 애초에 RAG 문제가 아니라는 것이다. 상품
탐색은 금리·조건 같은 구조화 데이터를 필터링하는 tool의 일이고, 법령
RAG는 다른 절반 — 보호한도, 설명의무, 청약철회 같은 제도·권리 질문을
담당한다. 질문 유형별로 분업하는 구조다.

- 상품 탐색 → finlife API tool (다음 단계)
- 제도·권리 → 법령 RAG (이번 단계)
- 단순 개념 → 모델 자체 지식
- 혼합 질문 → 두 경로 합성 (LangGraph 단계의 도입 근거)

부산물로 재미있는 사실도 알게 됐다. 금소법상 금융상품자문업은
등록제라서, 서비스를 "추천"으로 포지셔닝하면 미등록 영업 논점이 생길 수
있다. 그래서 "정보 제공·비교"로 포지셔닝하는데, 이걸 알려준 것이 바로
지금 인덱싱하려는 그 법이다.

## 교차 검증에서 고친 것들

방향을 정한 뒤 Gemini와 Codex에 같은 문제를 주고 교차 검증했다.

Gemini는 "LangGraph 기반 금융상품 비교 + 소비자 권리 보호 융합형"을
제안했다. 실질적으로 같은 조합이라 방향 확인이 됐고, 단서 두 개를
받아들였다. LangGraph를 간판으로 내세우지 말 것(도구는 근거가 생겼을 때
도입하는 것), 그리고 범위는 예·적금으로 유지할 것.

Codex 검증에서는 여섯 가지를 고쳤다.

1. **corpus를 2건에서 4건으로**: 예금자보호 한도 1억원은 법이 아니라
   시행령에 있고, 시행령에 "타 법률에 따른 보호 여부"가 설명사항으로
   명시되어 있다. 법률만 인덱싱하면 핵심 질문에 답을 못 한다. 금소법 +
   시행령, 예보법 + 시행령 4건으로 확정.
2. **finlife는 실시간이 아니라 공시 데이터**: 답변에 조회시각과 공시
   기준월, 가입 전 확인 안내를 붙여야 한다.
3. **개별 상품의 보호 여부는 법령으로 판정 불가**: 그건 공시와
   상품설명서의 영역이다. RAG는 보호의 범위·한도 규칙 설명까지만 한다.
4. **"추천 = 자문업 등록 대상"은 과장**: 등록 대상에는 이익 목적과
   계속·반복성 요건이 있다. 표현을 "비교 후보 제공 + 최종 확인은 공식
   상품설명서 안내"로 조정.
5. **상품설명서는 영구 제외가 아니라 조건부 도입**: 필요가 확인되면 원문
   커밋 없이 URL과 해시만 남기는 방식으로.
6. **LangGraph 도입 근거 재정의**: 단순 분기는 RunnableBranch로 충분하다.
   정보 보충 재질의, fallback, 상태 유지, 혼합 합성이 실제 근거다.

## 최종 결정

- 주제: 예·적금 이용자를 위한 소비자보호 법령 Q&A
- corpus: 금융소비자보호법 + 시행령, 예금자보호법 + 시행령 (4건)
- 수집: open.law.go.kr API로 XML 1회 수집, `data/laws/`에 원문 커밋
  (저작권법 제7조 근거)
- 수집 스크립트는 재현 가능하게 보존하되 정기 동기화는 하지 않는다 —
  법령의 저변동성이 선정 이유였으므로 1회 배치가 논리적으로 일관된다

한 문장으로 정리하면 이렇다. 내가 설명할 수 있는 난이도에서, 법적으로
재배포 가능한 구조화 데이터로, RAG → agent → MCP 확장의 "왜"를 전부
증명할 수 있는 주제.

결정 요약은 ADR 0004에, 평가 질문은 `docs/evaluation/rag-questions.md`에
남긴다.
