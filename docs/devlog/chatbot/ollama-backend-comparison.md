# Ollama backend 전환과 HF Transformers 비교

- 작성일: 2026-07-04
- 상태: Ollama backend 구현 완료, 비교 측정 완료

## 시작점

FastAPI 개발 중 두 가지 불편이 있었다. 모델이 서버 프로세스 안에 적재되어
`--reload`를 쓸 수 없었고(코드 수정마다 약 7.5GiB 재적재), 짧은 인사에도
답변까지 최대 20초가 걸렸다.

원인은 하나의 구조에서 나왔다. Transformers 모델이 FastAPI 프로세스 안에
살고 있었고, Transformers의 MPS 추론은 범용 커널이라 Apple Silicon에서
느리다. 이번 측정에서 fp16 생성 속도는 약 9~13 tok/s였다. 답변이 생성
상한(128 token)까지 이어지면 그것만으로 11~12초다.

## 결정

ADR 0003에 따라 Ollama를 두 번째 `Generator` 구현체로 추가했다. 같은
체크포인트 계열의 `qwen3:4b-instruct-2507-q4_K_M`을 사용하고,
`CHATBOT_BACKEND` 환경 변수로 backend를 선택한다. 기존 Hugging Face 구현은
비양자화 fp16 기준점으로 유지한다.

## 측정 방법

M2 Pro 16GB에서 같은 한국어 프롬프트 4개(인사, 적금 설명, 예금자보호제도,
금리 상식 검증)를 두 backend에 보냈다. 생성 상한은 둘 다 128 token, 각
backend는 warmup 1회 후 측정했다. HF 측정 전에 Ollama 모델을 메모리에서
내려 메모리 조건을 맞췄다. 두 런타임의 기본 디코딩 설정(temperature 등)이
완전히 같지는 않다는 한계가 있다.

## 결과

| 항목 | Ollama q4_K_M | HF fp16 (MPS) |
| --- | --- | --- |
| 생성 속도 | 52~54 tok/s | 9~13 tok/s |
| 128토큰 답변 응답 시간 | 2.65초 | 11~12초 |
| 모델 적재 | 약 3초 | 17.1초 |
| 가중치 상주 메모리 | 약 2.5GB | 약 7.5GiB |

개발 경험 개선이 목적이었으므로 `--reload`도 확인했다. 코드 수정 후
프로세스 재시작을 거쳐 새 응답을 받기까지 1.5초로, 기존의 전체 가중치
재적재 대비 사실상 즉시 재시작이 가능해졌다.

## 품질 관찰

4개 프롬프트 모두에서 두 backend의 답변이 동등한 수준이었다. 구조(마크다운
사용, 답변 흐름)와 내용 정확성이 거의 같았고, 4-bit 양자화로 인한 한국어
품질 저하는 관찰하지 못했다. 다만 표본이 4개뿐이므로 양자화가 무해하다는
결론이 아니라, 이 프로젝트의 용도에서 차이가 드러나지 않았다는 기록이다.
RAG 평가 세트가 만들어지면 같은 비교를 더 큰 표본으로 반복할 수 있다.

## 배운 점

- 체감 20초의 정체는 모델이 느린 것이 아니라 (1) 느린 런타임 × (2) 긴 생성
  길이 × (3) 프로세스 내 적재 구조의 곱이었다. 구조를 바꾸면 같은 모델로도
  다른 경험이 나온다.
- 양자화 모델 전환의 부수 효과로 가중치 메모리가 약 5GB 줄어, RAG 단계에서
  임베딩 모델을 올릴 여유가 생겼다.
- 프로세스 분리 자체는 자체 모델 서버로도 가능했지만, 그 경우 느린 런타임이
  그대로 남는다. 문제를 "reload가 안 된다"가 아니라 "모델이 어디에 살아야
  하는가"로 다시 정의한 것이 유효했다.
