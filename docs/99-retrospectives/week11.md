  - 2.5 flash는 10/16 지원 종료 예정
  - 이후 그래프 마이그레이션 이후 성능을 떨어트리지 않고 잘 마이그레이션 했는지 확인할 수 있고, 이후 에이전트로 확장 및 발전 이후 개선된 성능을 추적하는 등 베이스라인을 구축했다.
- 랭그래프로 마이그레이션을 진행
  - 단순 답변?(Ask-rag)부터 테스트하여 정상 출력을 확인 및 랭스미스 트레이싱 여부 확인

  - ui 수준에서 테스트 및 생성된 결과를 확인했다
  - 이후 2차 평가를 진행한다.
    - 여기서는 기존 체인 구조에서의 성능과 차이가 없어야 정상적인 마이그레이션이 진행된 지표로써 사용될 수 있다.

## 직접 이해하게 된 것
- 체인 구조를 랭그래프로 마이그레이션 한다는 것에 대해 모든 리트리버, 생성 등을 모두 그래프의 상태 스키마나 노드로 바꿔, 기존 체인 연결된 함수나 코드를 다 삭제해도 정상적으로 작동해야 정상적인 체인 -> 그래프 마이그레이션이라고 생각했다.
  - 코덱스와의 방향성 검토 및 질문을 통해 그래프 구조로 마이그레이션 한다의 의미를 이해했고, LCEL로 연결된 프롬프트 -모델 - 파싱(생성) 구조를 그래프에서 단순 호출함으로써 불필요한 노드나 엣지 연결을 줄일 수 있다는 것을 깨달았다.

## 막혔던 부분
- 랭스미스로 추적하며 평가 데이터를 이용해 평가하는 과정에서, 처음엔 24개 중 1개의 데이터만 랭스미스 웹에서 확인됐었어서 당황했다.
  - 알고보니 --all 옵션으로 평가 데이터를 다 실행 자체를 안했던거였어서 허무했다.
  - 하지만, 도중에 중간에 api free tier 호출을 다 써서 쿼터 초과 에러가 나거나, 한번에 --all로 수행하지 않고 한번에 평가가 오래 걸리지 않기 위해 10/14개로 나누어서 평가한 것을 웹 랭스미스에서 깔끔하게 하나의 베이스라인으로 합쳐서 남길 수 없다는 것을 깨달았다.
- 평가 과정에서 고수준 프론티어 모델(앤트로픽 api 이용)으로 평가하려고 했으나, 10 달러 크레딧이 일찍 소진되면 난감할 거 같아서 포기했다.
- 평가를 진행하고 보니, 세부 지표 이름이나, reference outputs 에서 참고한 부분이 아닌 여러 값이 들어가서 corpus_snapshot으로 2026-07-06이 쫙 떠있어서 매우 마음에 안들고 심기가 불편했다.

## 솔직한 회고
- 벡터스토어로 인덱싱한 로우 데이터에서 평가 데이터를 사람이 직접 검증하며 평가 데이터를 만드는건 얼마나 고된 일일지 생각해봤다.
  - 나는 gen ai로 수동 점검하며 수행했지만, 평가 데이터도 대충 정답을 맞추고 틀리고가 아닌, 더 많은 측면 및 관점에서 고려해서 만들어야 한다는 것을 느꼈다.
  - llm-as-a-judge를 이용해봤다. 역시 웹에서 랭스미스로 바로 직관적으로 확인할 수 있는게 흥미를 끌었고, 평가해서 남아있는 기록을 바탕으로 단순 선택만 해서 compare로 시각화하여 비교할 수 있다는 점이 진짜 편하다고 느꼈다.
