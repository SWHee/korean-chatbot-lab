# LangGraph 전환 후 A1 한 문항을 평가해본 기록

- 작성일: 2026-07-23
- Experiment: `rag-graph-v1-batch-333f32c2`
- 질문: 은행이 파산하면 내 예금은 얼마까지 보호받나요?

## 무엇을 확인하려 했는지

기존 LangChain RAG를 LangGraph의 `retrieve → generate` 흐름으로 옮긴 뒤, 같은
Dataset과 evaluator가 그대로 동작하는지 먼저 A1 한 문항으로 확인했습니다.

LangSmith Trace에는 다음 단계가 오류 없이 기록되었습니다.

| 단계 | 시간 |
| --- | ---: |
| 전체 Target | 17.34초 |
| LangGraph | 17.30초 |
| 검색 노드 | 0.79초 |
| 생성 노드 | 16.51초 |

그래프 실행과 LangSmith 연결은 정상적으로 보였습니다. 전체 시간의 대부분이 기존과
마찬가지로 로컬 생성 단계에서 사용된 것도 확인했습니다.

## 검색 점수가 0인 이유

A1의 필수 정답 조문은 예금자보호법 제32조와 예금자보호법 시행령 제18조입니다.
하지만 실제 상위 5개 검색 결과에는 두 조문이 모두 없었습니다.

```text
1. 예금자보호법 제1조
2. 예금자보호법 제36조의7
3. 예금자보호법 제24조의3
4. 예금자보호법 제35조의8
5. 예금자보호법 제36조의2
```

따라서 `precision_top_5`는 `0 / 5`, `recall_top_5`는 `0 / 2`로 모두 0이
나왔습니다. 평가 코드가 잘못 계산한 것이 아니라 실제 검색 실패를 반영한
점수였습니다.

검색 범위를 넓혀보니 시행령 제18조는 조문 기준 10위, 법 제32조는 12위였습니다.
시행령 제18조에서 실제 `1억원` 문장이 있는 청크는 청크 기준 22위였습니다. 정답
근거가 인덱스에 없는 것이 아니라 현재 top 5 밖에 있다는 것을 알게 되었습니다.

제1조는 질문에 들어 있는 `금융회사 파산`, `예금`, `보호` 표현을 직접 포함합니다.
반면 정답 조문은 `보험금 지급한도`, `부보금융회사`, `예금등 채권` 같은 법률 용어를
사용합니다. 긴 시행령 제18조가 여러 청크로 나뉘면서 필요한 항의 점수가 낮아진 점도
함께 확인했습니다.

## Reference Output의 역할

처음에는 Reference Output의 1억원 답안을 모델도 참고하는지 헷갈렸습니다. 하지만
Reference Output은 RAG가 답변을 만들 때 읽는 자료가 아니라, 실행이 끝난 결과를
평가하기 위한 모범 답안입니다. 현재 검색기와 생성 모델에는 `reference_answer`가
전달되지 않습니다.

즉 모델이 1억원 답안을 보고도 이해하지 못한 것이 아니었습니다. 검색된 top 5에
정답 근거가 없어서 생성 단계도 해당 내용을 전달받지 못했습니다.

## Judge 판정에서 발견한 점

생성 답변은 중심 내용에서 근거가 부족하다고 밝혔습니다. 하지만 마지막 참고
문장에서는 검색 문맥에 없는 `5,000만 원`과 잘못된 조문 정보를 덧붙였습니다.
그런데도 Gemini Judge는 Faithfulness `1.0`을 부여했습니다.

Dataset에는 `보호 한도는 5천만원이다`가 금지 주장으로 들어 있지만, 현재
Faithfulness evaluator는 이 목록을 Judge prompt에 전달하지 않습니다. 기본
Faithfulness 지시만으로도 근거 없는 주장을 찾아야 하지만 이번에는 놓쳤습니다.

그래서 이번 결과를 다음처럼 나누어 보았습니다.

- 그래프와 LangSmith 평가 연결: 정상
- 검색 Precision·Recall 0: 정상 계산된 검색 실패
- 답변: 근거 부족 안내 뒤 근거 없는 오래된 정보 추가
- Faithfulness 1.0: Judge가 문제 주장을 놓친 판정

## 다음 비교에서의 사용

LangChain 기준선에서도 A1 검색 점수는 0이었습니다. 같은 검색 실패가 재현됐으므로
LangGraph로 바꾸면서 검색 품질이 새로 나빠진 것은 아니었습니다.

전체 LangGraph 전환 평가까지는 Dataset, 검색 설정, prompt, 생성 모델, Judge를
기존 기준선과 동일하게 유지했습니다. 구조 전환 결과를 먼저 확인한 뒤 검색과 Judge를
각각 따로 개선해야 어느 변경이 점수에 영향을 주었는지 구분할 수 있기 때문입니다.
